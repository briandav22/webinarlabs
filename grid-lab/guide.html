Sydney Grid Lab

After a WAN circuit migration, the Sydney Infoblox grid member drops off the grid. Users are fine, the change gets closed, and the Grid Master's replication queue for Sydney keeps growing. The cause is a Palo Alto firewall denying the grid's UDP 1194 and 2114 on the new zone. Its flow records say so.

3 devices NetFlow v9 PAN-OS template 257 UDP 1194 tunnel · 2114 key exchange Kentik type paloalto
Victor · Infoblox

Grid Manager shows Sydney offline and its replication queue growing. DDI knows the member can't reach the Grid Master, but not where the traffic stops.

You · Kentik

Flow shows the member's traffic reaching the firewall and stopping there, marked Flow Denied, on the interface that moved during the maintenance.

      The PAN-OS record

      Template 257, "IPv4 Enterprise": 20 fields and 155 bytes a record, laid out exactly as a real PAN-OS firewall sends it. Nearly two thirds of every record is the App-ID and User-ID strings. These are the exact bytes of one denied retry from the Sydney member. Hover a field to find its bytes.

      Run it
      
    
      Run it on the lab droplet next to your Kentik agent, from webinarlabs/grid-lab. It uses Python 3 and the standard library only.
      
  
      
  
      
    
      Put the device IPs on loopback
      192.168.254.11, .21 and .31. Re-run after a reboot.
      
      
      sudo python3 grid_lab.py aliases --apply
      
    
      Load your Kentik credentials
      Use the same ~/.kentik.env as the other labs, with chmod 600 on it. sudo drops these variables, so use sudo -E if you run the Kentik commands under sudo.
      
      
      # ~/.kentik.env
export KENTIK_EMAIL="you@example.com"
export KENTIK_API_TOKEN="..."
export KENTIK_PLAN_ID="12345"

source ~/.kentik.env
      
    
      Onboard the three devices
      The firewall goes in as Palo Alto Networks Firewall (subtype paloalto). That type is what makes Kentik fill the Firewall Event and Application ID dimensions. The command reads the device list back and warns if the type didn't stick.
      
      
      python3 grid_lab.py kentik onboard --dry-run
python3 grid_lab.py kentik onboard
      
    
      Create the Grid lab role dimension
      This creates c_src_gridrole and c_dst_gridrole. The values are Sydney grid member, London grid member, Grid Master (dc1), Sydney office users and dc1 apps. It replaces all populators on these two dimensions.
      
      
      python3 grid_lab.py kentik dimensions --dry-run
python3 grid_lab.py kentik dimensions
      
    
      Send flow
      Type before, maintenance, impact or fix to jump to a phase, status for counters, or quit to stop. Use --phase impact instead of --timeline to stay on one phase.
      
      
      python3 grid_lab.py run --collector 127.0.0.1 --port 9995 --timeline "before:10,maintenance:3,impact:20,fix:10"
      
    
      Check what's on the wire
      listen decodes the firewall's records with its PAN-OS fields. preview prints a phase without sending anything.
      
      
      python3 grid_lab.py listen --port 9996 --firewall-only &
python3 grid_lab.py run --port 9996 --no-bind --no-console --duration 30
python3 grid_lab.py preview --phase impact
python3 -m unittest -v test_grid_lab

      Documented vs assumed
      
    
      How close this is to a real Palo, and what to check before showing it.
      
  
      
  
      
    
      Matched to a real firewall
        
      
      • The template packet: all eight PAN-OS templates (256–263), one per flowset, in the same order. It's identical to a captured one from byte 20 on.
        • 
      
      • Field lengths as sent: IN_BYTES 8 bytes, interfaces 4, App-ID 32, User-ID 64, NUL-padded. Palo's docs list shorter defaults.
        • 
      
      • One flowset per data record (159 bytes, no padding), header source ID 1, and a sequence number that counts packets.
        • 
      
      • Field IDs and order, firewallEvent values, and enterprise number 25461.
        • 
      
      • NetFlow profile defaults: template every 30 minutes or 20 packets, active timeout 5 minutes, port 2055.
        • 
      
      • Denied sessions are exported with event 3. Palo's community forum confirms you can't turn this off on the firewall.
        • 
    
      
    
      Chosen for the lab
        
      
      • The capture only had update (5) records, so the shape of created, deleted and denied records is the lab's choice.
        • 
      
      • A denied record carries the first packet, with output interface 0.
        • 
      
      • Short sessions get a created record for the first packet, then deleted records for the rest.
        • 
      
      • App-IDs openvpn, unknown-udp and not-applicable, and retries every 10 and 30 seconds.
        • 
      
      • Active timeout of 1 minute, which is valid in PAN-OS, so updates show up quickly.
        • 
    
      
    
      To check before the webinar
        
      
      • With Victor: what Grid Manager shows for an offline member, how it retries the tunnel and the key exchange, and whether it keeps serving DNS and DHCP locally.
        • 
      
      • In the portal: that the firewall's type is Palo Alto Networks Firewall and the dimensions fill in.
